# 新增板级支持

先确认 SoC（片上系统）、启动链和存储路径已有支持，再创建板级配置。
若同一平台机制可复用，主要改动落在 `components/board/<name>/`；
新存储/启动机制可能需要补平台能力与策略，不能把“只加一个配置文件”当作任何新板都成立的保证。

```text
components/board/<board>/
├── config.jsonnet       # 板身份、产品策略和硬件路由
├── overlay/             # 目标根文件系统覆盖
├── dtso/                # 板私有运行期设备树 overlay 源
└── patches/             # kernel / bootloader 等板级补丁
```

Jsonnet 文件的第一条非空内容必须是中文职责注释。
板级配置从现有相近板卡提取必要字段，硬件事实与产品策略分层，
不能照抄另一块板的电源、GPIO、分区几何或下载模式。
运行期 overlay 使用 `boot.overlays.board/enabled`；构建期 DTB 合并是独立机制。

实施顺序、最小配置、校验命令和验收记录见[扩展指南](../../docs/extension-guide.md)。
先用 `flange target list <board>` 和显式目标 `plan image` 确认配置/路由，
再在 Docker 构建，最后按该板的硬件说明上板。

配置可解析、镜像可构建、设备能启动及外设通过验收是不同结果；
在[板卡页](../boards/index.md)分别记录目标、介质、版本、通过项和未验收项。
