## TL;DR

硬件特性包（Package）把「一组配套的内核驱动 + 设备树 overlay + vendor
App」收敛成自描述单元。仓库内 Package 可由 board 通过 `packages: [...]`
opt-in（显式启用）；仓库内外的任意 Package 都可用
`flange package create|build|deploy|run|debug|log` 独立开发。Package 只负责编排，
实际工作复用既有 component 流水线或清单中的显式 argv action。

## 关键设计要点

- **清单**：`package.py` 导出 `PACKAGE = {"name", "components": [...]}`，`name` 必须与目录名一致。component `type` ∈ `oot-driver` / `devicetree` / `vendor`。
- **opt-in**：board 顶层 `packages` 字段，项可为字符串（整包默认集）或 dict（`{name, drivers: [...]}` 按需选子集）。
- **类型分发**（`expand_hardware_packages` 在 `resolve_config` 末尾注入 config）：
  - `oot-driver` → 合成 `kernel.oot_modules` 条目（绝对路径 + `{arch}/{cross_compile}/{kernel_src_abs}` 模板），复用 [[out-of-tree 模块]] 编译/安装。
  - `devicetree` → 注入 `boot.overlays.package` + `boot.package_overlay_sources`，作为 overlay 第四源由 device-tree-overlay 组件 cpp+dtc 编译（见 [[双 extlinux 配置]]）。
  - `vendor` → 指向包内含 `app.yaml` 的 App，复用 AppBuilder 编译、DebBuilder 打包与 App 的设备生命周期。
- **按需编译**：未被选中的 oot-driver 不编译、不装 `.ko`。
- **增量**：`packages_meta.{kernel_src_paths, overlay_src_paths}` 把包源内容混入 kernel / device-tree-overlay 内容哈希。

## 仓库外开发

先 `source <flange>/envsetup.sh` 并用 `lunch` 选择 target，然后可从任意目录
创建并操作 Package：

```bash
mkdir -p /work/vendor
cd /work/vendor

# 生成 /work/vendor/demo/package.py 和单个 vendor App
flange package create demo --type exec --build-system cmake
cd demo

# target 省略时默认当前目录
flange package build
flange package deploy --serial <adb-serial>
flange package run --serial <adb-serial> -- --port 9000
flange package debug --serial <adb-serial> -- --port 9000
flange package log --serial <adb-serial>
```

非 `create` 命令的目标可以是仓库内名称，例如
`flange package build meizu-e3-panel`；也可以是含 `package.py` 的绝对或相对
目录路径。相对路径始终相对调用者 cwd，而不是 flange 仓库。路径模式不会
自动修改 board 配置或 registry，Package 目录内即使有 `config.jsonnet` 也不会
被隐式加载。

Package 仅含一个当前 variant 可用的 vendor component 时会自动选择它；
含多个 vendor 时，`run` / `debug` / `log` 必须用 `--component <name>` 消除
歧义。`--component` 也可限定 `build` / `deploy` 的 vendor。`deploy` / `run` /
`debug` 默认先构建，`--no-build` 可复用已有产物。设备操作用
`--serial <adb-serial>` 指定设备；省略时只在恰好有一台处于 `device` 状态的 ADB 设备时
自动选择，无设备或多设备会在变更设备前失败。vendor 的默认运行、
调试与日志语义与 App 相同；默认 debug 需要 debug variant，无法推断的
App 类型应定义显式 action。

vendor component 的构建产物仍位于 flange 仓库的
`.build/target/<board>/<product>/<variant>/app/`。若当前 variant 包含 `oot-driver` 或
`devicetree`，且未用 `--component` 显式选中 vendor，则独立生命周期必须定义相应 action；否则
命令会明确失败，绝不自动刷写分区。

## 显式 actions 与信任边界

无法复用 vendor App 语义时，可在 `package.py` 中定义显式 action：

```python
PACKAGE = {
    "name": "demo",
    "components": [
        {"type": "vendor", "name": "agent", "dir": "app"},
    ],
    "actions": {
        "build": ["./tools/build.py", "--profile", "debug"],
        "deploy": ["./tools/deploy.py"],
        "run": ["./tools/run.py", "--mode", "safe"],
        "debug": ["./tools/debug.py"],
        "log": ["./tools/log.py"],
    },
}
```

action 名只能是 `build` / `deploy` / `run` / `debug` / `log`，每个值必须是
由非空字符串组成的非空 argv 列表。未知键、字符串命令、空 argv 或非字符串
元素都会在执行前被拒绝。显式 action 是对同名生命周期的自包含覆盖：
flange 不会再自动插入 vendor 构建、部署或默认运行步骤。`--no-build` 只用于
默认 vendor App 流水线，显式 action 应自行完成所需前置工作。`build` 在 Docker
内以 Package 目录为 cwd 执行，并应通过 `FLANGE_TARGET_DIR` 发布产物；其余
action 在宿主机 Package 目录中执行。设备 action 可读取已校验的
`FLANGE_ADB_SERIAL`；传入 `--component` 时还可读取 `FLANGE_COMPONENT`。

`--` 后的参数会不加修改地追加到 argv。例如：

```bash
flange package run . -- --port 9000
# 直接执行 argv：./tools/run.py --mode safe --port 9000
```

flange 不经 shell 拆词、展开或 `eval`，因此清单 argv 里的 `$VAR`、`;` 和
`$()` 都只是字面参数；需要环境值时应由脚本读取。但 `package.py` 本身是
加载时执行的 Python，且非 build action 直接在宿主机运行；只应加载可信
Package，并审查其 action 程序。

## 实例

- **meizu-e3-panel**（魅族 E3 MIPI-DSI 屏）：按 SoC 显示栈选 panel 驱动与背光驱动，按需 opt-in：
  - rock5b（RK3588，Rockchip BSP）：`simple-panel-dsi` 驱屏 + 板载 `pwm-backlight`；opt-in `[sec_ts]`，不取 sgm37604a。
  - [[radxa-cubie-a7a]]（A733，Allwinner BSP）：`allwinner,panel-dsi` 驱屏 + 屏自带 SGM37604A I2C 背光；opt-in `[sec_ts, sgm37604a]`，仅补两处 6.1→5.15 跨内核兼容垫片（`<linux/wakelock.h>` 缺失用 `__has_include` 回退 wakeup_source、i2c `.remove` 返回类型用 `LINUX_VERSION_CODE` 守卫）。
  - [[radxa-dragon-q6a]]（QCS6490，mainline drm/msm）：QCLINUX BSP 6.6.90 的 `drivers/gpu/drm/panel/` 是纯 mainline 风格，91 个驱动一型一驱、**没有**通用 DSI panel driver。包内随之新增第 3 个 oot-driver `panel_meizu_e3`（drm_panel 风格 ~250 行）+ SGM37604A I2C 背光（与 a7a 同款）；overlay 经 [[构建期 dtb overlay 合并]] 合到 base dtb（grub-with-dtb 无运行时 overlay）。opt-in `[sec_ts, sgm37604a, panel_meizu_e3]`。

> 印证 **devicetree component 按 board 路由 / oot-driver 跨 SoC 共享但按需 opt-in / 内核 API 差异由跨版本守卫吸收 / 缺通用驱动时包内补 OOT** 的分层模型。

## 易踩坑

- 老 BSP U-Boot（rock5b 为 2017.09）libfdt `overlay_symbol_update` 要求 overlay 内 label 符号为 `/fragment@N/__overlay__/...`：**新增根级节点必须包进显式 `fragment target-path="/"`**，否则根相对符号致 `FDT_ERR_BADOVERLAY`、boot 挂死。
- panel 与 dsi 间需 OF-graph 端口（`drm_of_find_panel_or_bridge(port=1)`），否则 `-19 找不到 panel`。
