## Context

基线为 radxa/kernel `7473a9fca2b08623319e497f4f811746baddb7bc`，运行内核为 7.0.2+，Q6A 未接显示器。组合负载现场 CPU0 的 hardirq（硬中断）占用达 90%，DP 为最频繁中断。UFS 错误计数未增加。

正常启动时 DP AHB（控制总线）`0xae90024` 读值为 `0x1000092d`，视频就绪和空闲图样状态位持续存在。只写零屏蔽 STATUS2 后中断停止，AUX/HPD 寄存器不变；写回 `0x924` 后一秒产生 57552 次中断，再屏蔽又停止。该实验确认风暴来自 STATUS2，但未证明残留状态的最初来源。

## Goals / Non-Goals

目标：空闲控制器不使能显示流中断；流启动仍可等待 video/idle 完成；中断处理与时钟关闭并发时不重新打开屏蔽位；记录原版、隔离实验和补丁的验证边界。

非目标：修改 UFS 驱动、关闭 GPU、默认禁用 HDMI、修复 msm 卸载异常。

## Decisions

1. STATUS2 的使能范围绑定到 link 与 pixel 两组时钟均已开启的生命周期。host_init 仅初始化 AUX/HPD，不无条件开启流中断。停止时在关闭任一相关时钟前屏蔽；链路重训练恢复时根据 pixel 时钟状态恢复。
2. 用自旋锁串行化 STATUS2 掩码更新与 ISR（中断服务程序）的读写确认；ISR 使用保存的当前掩码，避免原来的 ACK（确认）操作无条件重新打开全部使能位。只向上报告使能的状态，启用前在时钟开启状态确认残留事件。
3. 不通过调整 UFS 频率或中断亲和性掩盖显示中断源。整模块黑名单仅用于对照，最终删除。
4. 候选补丁通过 `flange --target radxa-dragon-q6a-default-debug build kernel` 在 Docker 中构建；部署前备份原模块并核对 vermagic（模块版本信息），不强制加载不兼容模块。
5. 共享平台新增补丁时同步 RUBIK Pi 3 的厂商内核 `exclude_patches`。其 default/desktop 产品使用不同源码，必须排除本补丁；mainline 产品继续继承平台补丁。配置回归保留排除集合与实际补丁集合严格相等的校验，补丁数量预期随清单更新；提交前执行完整 pytest 和全部 OpenSpec 严格校验。

## Risks / Trade-offs

- 无显示器，无法验证显示热插拔、链路训练、PSR（面板自刷新）与恢复 → 将这些场景保留为未完成验收，不能把无显示器测试称为完整显示回归。
- 本地构建与设备 Image 哈希不同 → 核对配置、模块版本和符号兼容性，优先只替换 msm 模块，不做全盘刷写。
- 用户态直接写 MMIO（内存映射 I/O）可能被 ISR 或 runtime PM（运行时电源管理）覆盖 → 仅用作有边界的诊断，产品修复必须在驱动中管理掩码。

## Migration Plan

保存原始日志与模块，构建候选补丁；备份后替换模块并重启，验证冷启动 IRQ 计数、CPU＋随机/顺序 I/O、UFS 错误与 dmesg。失败时恢复原模块；无显示环境可临时使用显式记录的 msm 黑名单规避。

## Open Questions

- 开机残留 STATUS2 状态与固件、时钟交接、复位的具体关系尚未证明；晚加载 msm 未出现残留状态。
- 补丁的显示输出与热插拔回归需要接入显示设备后验收。
