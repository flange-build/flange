## Context

用户的实际 khadas-vim3/default/debug 日志在 kernel 阶段混入 Git fetch、reset 和 worktree 输出；单行状态被插入成多段残行。kernel 约耗 47 分钟，按 7 个组件计算的进度仍从 0% 到 14%，不能帮助判断剩余工作。最后 recoveryctl 运行入口校验失败，真正原因被错误框、耗时表和两层 CLI 包装反复展示，最后一行变成容器退出而非需要修复的配置。

当前系统与独立 App/Package 构建已共享 BuildOutput、目标锁和 build.log 轮转；这次沿用这些边界，修正终端所有权、文案和进程输出通道。recoveryctl 的安装布局以 `/usr/sbin/recoveryctl` 为准，构建器默认 `/usr/bin/<name>` 仅适用于未声明自定义入口的应用。

## Goals / Non-Goals

**Goals:**

- 新人在任意时刻能回答：构建哪个目标、正在做什么、是否仍在运行、最终结果如何、失败后去哪里查看和怎样继续。
- NORMAL 只呈现任务层级和必要证据；VERBOSE 提供完整工具输出；所有级别保留完整日志。
- 工具进度、活动行与最终诊断经过同一终端输出所有者，避免竞争 stdout/stderr 和重复异常包装。
- recoveryctl 的声明、安装清单和执行入口相符，并保留严格校验。

**Non-Goals:**

- 不预测完整构建剩余时间，不为不同工作量组件赋相同时间权重。
- 不改变构建计划、缓存语义、目标选择或产物格式。
- 不执行真实设备操作；完整镜像构建是否通过须由独立的实际运行证明。

## Decisions

### 1. 终端输出由一次构建的 BuildOutput 统一管理

源码准备、Git 和编译命令通过捕获通道把 stdout/stderr 交给输出服务，原始行保留到 build.log。NORMAL 不让工具自己的 `\r` 进度直接写入终端；VERBOSE 也需先暂停或清除活动行再展示。宿主 Docker 调用只承载内层已格式化输出，不重复把它当编译原文再包装一层。

`builder/process.py` 的 `run_logged` 负责流式捕获，查询命令保留返回值并记录诊断；
超时和取消终止对应进程组。SourceManager 接收输出实例，DockerRunner 沿同一接口传递工具原文。

单纯降低颜色亮度无法修复并行写终端造成的交错；给每个子进程各建进度条又会增加竞争。统一所有者既保留原始诊断，也明确谁负责清除状态行、计时和收尾。

### 2. 正常模式使用目标、阶段、动作和紧凑结果

开头用短文本表达目标与本次构建请求；阶段可显示真实顺序和总数，不能将其换算为百分比。当前动作使用业务含义，例如“准备内核源码”“编译内核”，避免默认暴露资源摘要、worktree 内部事件和缓存实现字段。

活动行只显示当前阶段/动作与已耗时，终端正文的排版宽度上限约为 96 列，不把耗时推到宽终端的最右边。结束输出阶段结果计数、实际总耗时和日志位置；详细模式可以追加简洁的组件耗时列表，不绘制耗时占比条。阶段完成不等于实际 App 重新编译，逐项 App 缓存状态继续来自构建报告。

### 3. 开始信息立即出现，耗时只来自真实事件

NORMAL/VERBOSE 在非 TTY、无颜色或无法重绘时，步骤开始立即写一条普通状态，步骤结束再输出真实结果；QUIET 保留最终摘要。不能等编译 45 分钟结束才首次显示“编译内核”。有能力的交互终端最多显示一条原地更新的活动行；完整阶段、错误和日志路径仍需落成可复制的普通文本。

同一组件缓存复用和成功编译分别显示，取消不得变成失败步骤或成功结果。阶段计数仅反映完成数量，耗时不推算 ETA。
`status(msg)` 仅说明即时事实；实际操作用 `step(label)` 或 `spinner_start` / `spinner_stop`
定义开始与结束。计时不从相邻状态文案推断，避免将后续编译时间算入“源码已就绪”等通知。
步骤支持嵌套，阶段与步骤统一采用 monotonic（单调时钟），不受系统时间调整影响。

### 4. 根因只解释一次，外层只传播状态

一次失败保留失败阶段/动作、异常原因、相关命令及必要的尾部上下文，完整 traceback 写入日志。已经呈现过的失败以可识别的执行状态跨容器/CLI 传播；外层不得再次追加相同原因或用笼统的 Docker exit 信息覆盖根因。容器尚未启动、通信协议异常等未呈现过的外层失败仍必须给出独立诊断。

系统与独立 App/Package 的容器执行共用 `builder/build_result.py` 的失败回执。
每次调用使用独立临时目录与 request_id，读取时核验 schema_version、调用身份、退出码和已呈现标记；
不匹配或缺失的回执不能压制 Docker 原始故障。回执是内部传递格式，公共机器接口继续使用 CLI JSON envelope。

恢复提示复用用户本次语义：默认 image 请求显示 `flange build`，指定 kernel 显示 `flange build kernel`；保留适用的工作区与临时目标信息。配置错误应先修复再重试，不默认建议 clean 或 force。

### 5. recoveryctl 使用显式非默认运行入口

在 AppSpec 声明 `runtime.executable: /usr/sbin/recoveryctl`，不迁移已有系统安装位置。验收确认报告和安装树使用同一路径、权限可执行，以及两个受支持用户态架构的最小打包流程。继续让其他错误运行入口在发布前失败。

## Risks / Trade-offs

- [NORMAL 隐藏工具细节] → 完整输出保留在日志，失败展示相关上下文，`-v` 可展开。
- [压制重复错误误吞真正的外层故障] → 只有具备已呈现标记的失败才去重，容器启动失败和未知异常仍独立报告。
- [Git 的回车进度与非换行输出形成残行] → 进程输出通道统一归一化，再由 BuildOutput 管理终端刷新。
- [长步骤没有百分比让用户担心卡死] → 开始即显示真实动作，有能力的终端持续显示已耗时，日志保留流式原文。
- [修复单个 App 被误解为整机完成] → validation.md 分开记录输出测试、recoveryctl 最小构建和未执行的完整镜像/实机验收。

## Migration Plan

沿用现有命令、输出级别、JSON envelope 和日志路径，无需迁移工作区。新日志在下一次构建按既有策略轮转。recoveryctl 清单修改作为构建输入自然触发对应 App 重新打包，用户修复后可以重试原始构建请求。

## Open Questions

没有新增公开 CLI 选项或待定迁移决策。最终验收结果与未验证边界见 validation.md。
