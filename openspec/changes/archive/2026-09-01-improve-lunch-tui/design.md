# 设计说明

## 决策 1：层级只由身份投影构造，配置表另走一条路

`resolve_config` 求值单个目标实测 **1.3 秒**。如果右栏跟着光标同步求值，
每按一次方向键就要卡 1.3 秒，界面比原来的编号列表还难用。

所以拆成两条路径：

- **层级**由 `discover_boards()` 的身份投影构造（platform / soc / products /
  variants 都在里面），毫秒级，导航永远不卡。
- **配置表**只在光标停到末级目标时按需求值，交给后台线程，主循环带 150ms
  超时轮询按键，算完自然重绘。同一目标只算一次。

一条测试钉住这个前提：`build_target_tree` 执行期间调用 `resolve_config`
直接判失败。

## 决策 2：结果经文件回传，不走 stdout

子进程改不了父 shell 的环境变量，所以界面不能自己 `export`。而常见的
`selected=$(python -m ...)` 写法在这里不可行：`$(...)` 会捕获 stdout，
curses 的绘制全部被吞掉，用户看到的是黑屏。

因此界面直接占用终端，选中结果写到 `--out` 指定的临时文件，由 `envsetup.sh`
读回后走既有的导出与持久化路径。取消则不写文件 —— "没有选择"和"选了空串"
因此是两种可区分的状态。

## 决策 3：用标准库 curses，不引入 TUI 框架

界面的复杂度是"一棵可折叠的树 + 一张只读表"。为它往构建环境里加一个第三方
依赖，与 `flange` 自身"构建环境要可复现"的主张相悖 —— 而且 `pyproject.toml`
的每一个依赖都要在容器与宿主机两侧都装上。

代价是要自己处理两件事：**中文双宽字符**的对齐与截断（`display_width` /
`truncate` / `pad`），以及**越界写入**（终端缩小时 `addnstr` 会抛
`curses.error`，统一吞掉而不是让界面崩掉）。

## 决策 4：绘制与逻辑分离

`TreeView` 与 `SummaryLoader` 都不 import curses。理由是最容易写错的部分不
在绘制上，而在：折叠一个未展开的节点时光标该去哪、过滤命中了却因为没展开
而看不到叶子、配置还没加载完时右栏显示什么。这些在有终端的前提下很难测，
分离之后是普通的单元测试。

绘制层只剩"把行画出来"，PTY 冒烟测试确认它确实能渲染即可。

## 决策 5：末级三段直接取自树，不解析目标名

`SummaryLoader` 最初调 `parse_target(target)` 把自己拼出来的
`<board>-<product>-<variant>` 再解析回去。这既多余，也把界面绑死在"目标必须
能通过全局校验"上 —— 而 board 名本身含连字符，解析要靠试探。

改为由叶子节点沿父链直接取出三段（`leaf_parts`）。

## 决策 6：摘要是挑选过的表，不是配置转储

求值结果有 25 个顶层键。全倒出来等于把配置分层想替用户省掉的工作又还给他。
表按用户选目标时真正要确认的东西分节：身份、架构、内核、Bootloader、
存储与分区、Rootfs、功能开关。

字段缺失显示 `—` 而不是报错：摘要用于浏览，不该因为某块板没声明某个可选
字段就打断。分区行优先显示 `image_size` 而非 `size` —— 前者才是实际做出来的
镜像大小。

## 决策 7：PgUp/PgDn 翻的是右栏

完整配置表约 40 行，比常见终端高度长。左树有方向键，右表原本一个键都没有，
够不着的行只能干看着。所以把翻页给右栏，左树保留方向键与过滤。
