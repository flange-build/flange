## Why

用户的系统构建在 rootfs 安装 sudo 时因 `Permission denied` 失败，已有日志还暴露清理命令可能覆盖真正失败命令的诊断上下文。同一特权容器中的对照实验已确认：当前 macOS 共享目录无法保留 Linux root 对只读文件的写入和预期 UID，原生 overlayfs 可正确完成；Docker 提供 Linux 进程环境，但不自动补全共享目录的文件系统语义。

## What Changes

- rootfs 与 recovery 的可变文件树在满足 Linux 权限、所有权和链接语义的构建存储中完成解包、APT 安装、定制及成像；普通宿主共享目录不能仅因大小写敏感就被视为合格。
- 使用有作用域的容器 `/var/tmp` 临时目录承载活树，保持工作区、目标隔离、内容校验和宿主可见最终产物契约；镜像输出与基础快照归档继续使用工作区持久化目录。
- 原始 ubuntu-base 解包与基础快照保存/恢复显式保留数字所有权、扩展属性、文件 capability（能力属性）和 ACL（访问控制列表），避免缓存恢复后的目标权限与首次构建不同。
- 在命令失败时保留该命令的诊断快照；后续卸载、恢复文件等清理命令继续写完整日志，但不能覆盖原始原因与相关上下文。
- 通过真实 Docker 文件系统语义与最小 rootfs/APT 验证复现和验证修复，并同步新手指南、ProjectSpec 与规格，不将单项验证扩大为完整镜像交付。

## Capabilities

### New Capabilities

- `rootfs-build-storage`：rootfs/recovery 工作树的 Linux 文件系统语义、目标隔离、产物发布与失败清理边界。

### Modified Capabilities

- `build-output`：失败上下文随失败命令保存，后续清理不能使终端诊断变成无关命令的输出。

## Impact

- 涉及 rootfs/recovery 公共编排、构建存储、Docker/挂载生命周期、基础快照与产物收集的连接边界；准确修改文件随最终实现记录。
- 涉及 BuildOutput、进程执行通道和 chroot 清理阶段的错误传播。
- 系统构建、恢复系统构建与失败诊断测试；ProjectSpec、开发/入门指南中的文件系统与故障恢复说明。
- 公共构建命令与最终目标产物位置保持现有契约；不得通过改变 sudo 目标权限或关闭校验掩盖构建存储问题。

## 非目标

- 不修改目标系统既定的 sudo 安全策略或把只读目录一律改成可写。
- 不将全部源码与用户工作区强制搬迁到尚未验证的存储方案。
- 不更换发行版包集合，不以绕开 sudo 安装宣称问题已解决。
- 不执行设备刷写、部署或 Recovery 切换；完整镜像是否通过由对应实际构建单独证明。
