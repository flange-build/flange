## Context

当前 AppBuilder 在资源工作目录构建和打包，然后将 staging 安装树复制到临时 `publish/install`，校验后原子发布资源目录。真实 `radxa-rock5b-desktop-debug` 构建的 `rkmm-mpp` 在 `shutil.copytree(..., symlinks=True)` 阶段报告 `ENOENT`；检查源树和失败后的目标树时，动态库的 `.so → .so.1 → .so.0` 链均完整。

真实存储探针已确认失败链路为 `shutil.copystat → _copyxattr → os.setxattr(..., follow_symlinks=False)`：当共享 `fuseblk` 卷中的新建链接目标尚未落地时，扩展属性写入返回 `ENOENT`。同一 stage 复制到 Linux 原生 `overlayfs` 成功，复制到共享卷新临时目录稳定复现三条动态库链接错误；链接 `utime` 成功。证据在 `/tmp/flange-app-symlink-storage-probe.log`。该结论仅描述本次实测存储行为，不推断所有共享文件系统均相同。

发布目录已经包含文件也不代表发布成功：manifest 与请求报告仍必须走完整校验。

## Goals / Non-Goals

**Goals（目标）：**

- 明确 App 文件树中的对象语义：链接保存链接文本，普通文件保存内容和模式，目录保存结构和模式。
- 使链接复制不依赖目录遍历顺序或链接目标当前可访问性。
- 修复 App 安装树、隔离源码副本、debug-source 快照和 Package 源码快照复制边界，并继续报告真实 I/O 失败。
- 验证真实库发布后，继续完成用户请求的 desktop 构建；分别记录发布与整机验证结果。

**Non-Goals（非目标）：**

- 不调整链接内容、库 ABI、DEB 拆分规则或 ELF 架构门禁。
- 不把链接替换为目标文件，不增加“遇到 ENOENT 即忽略”的通用异常处理。
- 不改 rootfs 快照的 UID/GID、ACL 或 capability 契约；App 源码复制不等同于 rootfs 归档。

## Decisions

### 1. 先确认失败操作，再选最小复制实现

实现以已确认的链接扩展属性复制边界为依据，不给特定 App 或文件名增加例外，也不吞掉所有 `ENOENT`。无需移除动态库链接或更改原有源树。

### 2. 链接按对象复制，普通对象保留权限

复制逻辑先识别链接，读取其原始目标文本并创建同样的链接，不为链接调用可能跟随目标的元数据复制。常规文件和目录仍保留其实际内容、结构与模式位；目录权限在子项复制完成后应用，避免只读目录阻碍填充。

这使相对链接、绝对链接、目录链接和暂时悬空的链接具有一致的复制行为。链接目标是否符合某种 App 安装策略仍由现有收集与验证边界决定；复制函数不新增目标存在性条件。

### 3. 保持原子发布与可诊断失败

复制失败继续抛出原始 I/O 错误，未通过完整输出验证前不得替换上次成功目录或写入成功报告。不能因失败后的目标树“看起来完整”就把该次执行当成功。若引入共享复制配方，其变化必须影响使用该配方的 App 输入身份。

### 4. 收敛实际复用边界

新增独立 `builder/file_tree.py`，提供 `copy_entry` 与 `copy_tree`。链接只执行 `readlink` 与 `symlink`；普通文件使用 `copy2`，目录递归完成后调用 `copystat`，保留空目录。App 安装树、隔离源码和 debug-source 快照，以及 Package 源码快照复用该实现。

构建目录排除规则、约定文件安装映射与 manifest 输出集合保持原语义。App/Package 配方输入加入 helper 身份。系统引擎和内核复制路径保持现状，避免无关组件因公共模块修改而缓存失效。

## Risks / Trade-offs

- 省略链接元数据复制可能改变链接自身时间戳 → 本契约关注链接类型和目标文本；不能借此省略普通文件和目录的权限。
- 自定义递归复制容易漏掉嵌套目录或覆盖行为 → 覆盖链式/悬空/目录链接、已有目标和普通目录模式的回归用例。
- 共享卷故障可能与链接复制以外的 I/O 有关 → 保留原始错误，不以宽泛重试或异常吞噬掩盖磁盘、权限及源文件消失问题。
- 配方变化后旧 App 缓存可能复用 → 确认复制实现属于指纹输入，并通过真实构建验证。

## Migration Plan

不迁移用户 App 和工作区。修复后重跑同一 desktop 构建，允许通过现有计划复用未受影响的阶段；App 发布继续使用原有目录和报告 schema。回退时只撤回复制实现，不能恢复未验证的半成品为成功产物。

## 验证边界

根因探针、文件树与发布回归、真实共享卷 fixture、`rkmm-mpp` 发布和完整 desktop 构建均已完成验证。
最终 GPT、分区内容、文件系统与 manifest 的只读验收见 [validation.md](validation.md)；
最小复制、App 发布、整机镜像与板卡实机验证是不同边界，本次未进行板卡刷写或启动测试。
