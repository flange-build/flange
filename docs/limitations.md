# 能力范围与验证边界

本页描述当前能力的边界。具体命令见[开发指南](development-guide.md)，硬件结论以
[板卡页](boards/README.md)注明的目标、介质、时间和证据范围为准。

## 可以依赖的行为

- 工作区持有自己的目标、输出根、App 注册与层集合；Docker 负责目标编译和系统成像。
- 系统与 App 计划使用声明输入、完整依赖闭包和产物清单；缓存同时检查输入身份与实际输出。
- rootfs/recovery 共享基础阶段计划，定制、账户、模块和 overlay 在基础快照之后执行。
- App/Package 支持计划、构建、部署、运行、测试、日志和调试，设备会话关联准确产物。
- Ubuntu/DEB 是核心默认组合；其他发行版、包格式与独立 SDK 通过扩展层提供。

## 当前没有提供的完整服务

| 范围 | 当前边界 |
| --- | --- |
| 严格复现与发布 | Docker 统一环境，但远端 branch、APT 软件源和外部层仍可能变化；没有自动锁定所有输入的发布服务 |
| SDK 分发 | 可选择独立 sysroot/工具链并记录身份，不自动生成可分发的完整 SDK 或全系统符号仓库 |
| 软件供应链 | 有输入摘要、包清单和产物校验，不等于完整 SBOM（软件物料清单）、签名或来源证明 |
| 远程更新 | Recovery 是 USB 在线维护；没有通用 OTA（空中升级）、A/B 更新管理或网络烧录服务 |
| 自动硬件验收 | pytest 和配置矩阵不替代所有板卡、产品、介质和外设的实机回归 |
| 多层来源管理 | 本地声明顺序与依赖校验已支持，不自动下载、同步或锁定层仓库，也不逐字段解释任意 Jsonnet 表达式来源 |
| 性能比较 | 不保证比 Buildroot/Yocto 快多少；需在相同目标、输入和缓存条件下实测 |
| 外设固件 | Cardputer/Tab5 的 ESP-IDF 工程独立构建，尚未纳入标准 flange Docker 工具链 |

## 如何阅读验证结论

| 证据 | 证明范围 |
| --- | --- |
| `target show` / 配置矩阵 | 配置能解析并通过当前校验 |
| `plan` / `why` | 本地可见输入、依赖与缓存理由；不证明远端内容或实际编译成功 |
| pytest | 执行到的单元/模拟/集成断言；skipped 表示该检查未执行 |
| Docker 构建与清单 | 指定环境实际生成并校验了产物 |
| 刷写记录 | 对指定设备执行了什么写入；中断或 writing 状态不能视为完整成功 |
| 板卡功能记录 | 指定产物与硬件的实际观察；不能推广到其他变体或未接外设 |

遇到问题先保留完整 target、flange 版本、宿主环境、构建日志和设备串口输出，
再按[维护指南](maintenance-guide.md)定位。当前板卡页汇总可复用的最终结论，历史过程可在 Git 中查询。
